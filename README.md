# SEDNA CARE 院舍照護管理原型

一次請求從進程啟動到頁面渲染，按依賴順序分七層：

- L1 啟動層讀配置、建庫、灌示範資料、載入知識庫、掛路由與靜態檔案。
- L2 資料層定義表結構、連線管理與示範資料生成。
- L3 身份層做登入簽發、請求鑑權、角色守衛與院舍隔離。
- L4 規則層把「180 天評估到期」「本週資助目標達成率」這類業務判斷從介面裡抽出來，純函數、可單測。
- L5 介面層每個模組一個檔案，全部透過 L3 的依賴注入拿到當前使用者，透過 L4 拿判斷結果。
- L6 知識庫層獨立於業務資料，文件切分、檢索、帶出處生成三步串起來。
- L7 前端無建置步驟，三個 JS 檔按依賴順序載入。

`app.py` 是最外層入口，`core/deps.py` 是貫穿全篇的樞紐，所有介面都從它拿身份與資料範圍。

```text

│   ├── deps.py                         # 樞紐：current_user、require、四種範圍函數
```

```bash

pip install -r requirements.txt
python app.py
```

| `wong` | 黃淑芬 | 組長 | 本院舍的全部節次與住客 |

職員被擋下時後端回 403，不是前端把入口藏起來。真正的判斷全部在 `core/deps.py`。

側欄不再把沒權限的項目拿掉，改成**顯示但掛一把鎖**。拿掉的話三種角色的側欄長度不同，

## L1 啟動

進程起來要按固定順序做五件事，任何一步依賴前一步，順序不能換。

按序讀兩個檔案：

1. `config.py`：一處集中所有可變量。資料庫路徑、token 簽名密鑰、模型端點與金鑰、模型名。密鑰全部走環境變數，讀不到給一個僅供演示的預設值。`DEMO_MODE` 開關打開時問答不調模型，用於現場沒有網絡。

2. `app.py`：入口。先檢查相依套件，缺哪個就印一行中文提示告訴使用者裝什麼，而不是甩一串 traceback。接著建庫、灌示範資料、載入知識庫、掛介面路由、掛靜態檔案。建庫和灌資料都是冪等的，反覆啟動不會重複灌。介面統一掛在 `/api` 下，靜態檔案掛在根路徑，兩者不衝突。

## L2 資料

八張表，一處定義。所有表都帶 `facility_id` 用於院舍隔離，都帶 `is_deleted` 走軟刪除，都帶建立時間。

按序讀三處：

3. `core/schema.sql`：建表語句集中在這裡，不散在 Python 程式碼裡。八張表分別是院舍、員工、住客、工作節次、表單模板、表單提交、留痕、評估記錄。

   索引是量出來的，不是憑感覺加的。`form_submissions(session_id)` 這一條非加不可：合規看板的「已完成但未填表」是 `NOT EXISTS (... WHERE x.session_id = s.id)`，沒有索引時每一節都要全表掃一遍表單提交，成本隨兩張表相乘。示範資料 3080 節時 188ms 看不出問題，三間院舍跑三年是 15 萬節，同一句要 18.7 秒，頁面直接白掉；加上之後 65ms。

   反過來，憑直覺加索引會出事。留痕查詢在 50 萬筆時本來就只要 1ms（`idx_audit_created` 倒著走，取滿 200 筆就停），替它加一條 `(facility_id, created_at)` 之後反而變成 41ms——SQLite 改用了新索引，然後還得排序。**慢了 40 倍。** 所以這一層的規矩是：先量再加，加完再量一次。

   表單模板和表單提交分開兩張表，提交記錄裡存模板代碼加版本號。模板改版之後舊記錄仍按當時的版本渲染，這是業務系統最容易踩的坑，結構上先留好。

4. `core/db.py`：一個上下文管理器負責開關連線與提交，`query` 和 `execute` 兩個薄函數包住游標操作，回傳字典而不是元組。`init_db` 讀 `schema.sql` 一次性執行。全篇不再有第二處直接開連線的地方。

5. `domain/seed.py`：示範資料生成。三間院舍、每間三十位左右住客、近三個月的節次與表單提交。

   每位治療師帶一份固定的住客名單（caseload），不是每天從全院隨機抽人。隨機抽的話三個月下來每位治療師都會碰過全院每一位住客，「本人負責的住客」這個範圍就等於「整間院舍」，權限分層名存實亡。名單之間留 20% 重疊，模擬真實的補位與跨組協作，完全不重疊反而不像真的。

   幾個刻意的細節：隨機種子固定，每次生成結果一致，演示可複現。姓名用港式繁體，且員工姓名不進住客名字池，同一個名字同時出現在治療師和住客欄，懂業務的人一眼看出是生成資料。服務類型按軌道分池，認知障礙症軌道不排肢體訓練。節次狀態按真實比例分布，「未能出席」保持一定佔比，合規看板要用到它。另外刻意留下一批「已完成但未填表」的節次，那是紙本轉系統時最常見的缺口。

## L3 身份與權限

三種角色，職員、組長、管理員。同一個介面三種角色看到的資料範圍不同，這個差異不寫在每個介面裡，統一收在 `deps.py`。

按序讀三個檔案：

6. `core/security.py`：密碼用 sha256 加鹽雜湊。token 不引入 JWT 套件，用標準庫 hmac 自己簽，格式是使用者 id 加過期時間戳加簽名三段拼接，校驗時先驗簽再驗過期。這樣少一個相依，程式碼也就三十行。

7. `core/deps.py`：全篇樞紐。`current_user` 從請求標頭解出 token、校驗、查庫回傳使用者物件，失敗拋 401。`require(*roles)` 生成一個依賴函數，角色不在允許清單裡拋 403，介面只要在簽名上加一行就完成鑑權。

   範圍過濾有四個函數，不是一個，因為業務上本來就是四種問題：

   | 函數 | 問的是 | 職員看到 | 用在 |
   |---|---|---|---|
   | `scope_filter` | 這節誰做的 | 指派給本人的節次 | 工作計劃、今日節次、未填表 |
   | `resident_scope` | 誰沒做到 | 本人負責的住客 | 合規看板、今日的到期與落後 |
   | `facility_scope` | 這位住客是誰 | 本院舍全部住客 | 住客主檔、軟刪除 |
   | `audit_scope` | 誰動過什麼 | 無權限（403） | 留痕查詢、首頁最近動態 |

   `resident_scope` 和 `facility_scope` 的分工是刻意的，也是踩過的坑。合規看板問的是「誰沒做到」，那是**問責**，問責必須落到人；住客主檔問的是「這位住客是誰」，那是**查檔**，查檔限到人反而擋住正常協作——同院舍的治療師本來就要查得到彼此的住客，不然交更和補位沒法做。

   同一個 `facility_scope` 套在兩種問題上，結果就是職員看到整間院舍的未達標名單：既不是他的責任範圍，也讓權限演示當場失去說服力。這個 bug 真的發生過，修正記在 `api/compliance.py`。

   住客表上沒有負責人欄位，負責關係由工作節次建立：誰被指派了這位住客的節次，誰就負責這位住客。走子查詢而不是在 `residents` 上加一個會跟排班脫節的冗餘欄位。

   把範圍過濾收在這幾個函數裡，是因為權限漏洞幾乎都出在「幾十個介面裡漏寫了一個判斷」。所有查詢共用同一段條件，就沒有漏寫的餘地。

8. `core/audit.py`：留痕寫入。參數是操作人、動作、實體類型、實體 id、改前、改後。改前改後都序列化成 JSON 存下來。這張表沒有更新和刪除介面，只能追加。

## L4 業務規則

從介面裡抽出來的純函數，不碰資料庫、不碰請求，輸入輸出都是普通資料結構，可以直接單測。

按序讀一個檔案：

9. `domain/rules.py`：四組函數。

   第一組算評估周期，給定上次評估日期與當前日期，回傳距離 180 天到期還有多少天以及分級。「從未評估」單獨歸一類而不是併進「已逾期」，因為稽查時這兩種情況性質不同，一個是漏做，一個是沒有記錄。

   第二組算週目標達成率，回傳百分比與紅黃綠分級。目標為零時視同達標，避免除零，也避免把沒有服務權益的住客標紅。

   第三組是 `pick_week`，決定統計哪一週。本週才過一兩天時，達成率必然全線落後，那個數字沒有參考價值，所以預設改看上一個完整週，並在回傳體標明看的是哪一週和為什麼，而不是默默換掉。

   第四組把資料庫裡的原始狀態映射成介面上的徽章類型。

## L5 介面

每個模組一個檔案，全部掛在 `/api` 下。所有需要身份的介面都透過 `Depends(current_user)` 拿使用者，所有需要限範圍的查詢都調 L3 那四個範圍函數之一。

按序讀七處：

10. `api/auth.py`：登入接收帳號密碼，校驗後簽發 token 並寫一條留痕。`/me` 把 token 解出的使用者物件回傳，前端重整頁面時用它恢復登入態。

    `/scope` 把當前身份的視野量化：負責幾位、可查閱幾位、幾間院舍、還有多少不在範圍內。權限的本質是「看不到的東西」，而看不到的東西沒法展示——「職員少了一個選單項」是消極證據，觀眾感受不到沒發生的事。這個介面把被擋掉的**量**算出來，讓消極證據變成積極證據。回傳的分母是聚合計數，不含任何住客身份、床號或狀態，洩露的只有「還剩多少」這一個數字。

11. `api/residents.py`：主檔列表走院舍範圍過濾。匯入介面接收 xlsx，用 openpyxl 讀表頭做欄位映射，逐列校驗床號唯一性、性別、資助類別、服務軌道、日期格式。

    校驗失敗的列不寫庫，收集成錯誤清單一併回傳，讓使用者知道第幾列為什麼沒進去，而不是整批失敗或靜默丟棄。模板由 `/residents/template` 動態生成供下載。

12. `api/sessions.py`：工作計劃。回傳體帶上 `scope_label`，前端據此顯示「你正在查看：本院舍全部節次」這行字。現場切換帳號演示時，這行字就是權限隔離最直觀的證明。

13. `api/compliance.py`：三個介面。週目標達成率、評估到期追蹤、已完成但未填表。判斷全部來自 `rules.py`，這裡只取數與拼裝。

14. `api/audit_view.py`：留痕查詢。簽名上加 `Depends(require("supervisor", "admin"))`，職員拿到 403；組長再經 `audit_scope` 限到本院舍。這裡漏掉範圍限制的話，正好是在「證明權限隔離」的那一頁上把隔離漏掉，切帳號演示時第一個被抓到的就是它。

    `limit` 走 `Query(200, ge=1, le=500)`，上下界都卡。原本寫的是 `min(limit, 500)`，負數會漏過去，而 SQLite 的 `LIMIT -1` 意思是「不限制」——`?limit=-1` 就能把整張表拖出來。現在只有一百多筆看不出問題，留痕表長到百萬級時這是一發即中的。夾值要在邊界上做，不要在 SQL 前一行做。

    回傳的是寫入時就生成好的中文摘要，界面直接顯示那句話。需要細節時展開的是一組「欄位、原本、改為」，欄位名同樣是中文。**界面上永遠不出現 JSON**——留痕這一頁的讀者是管理層與稽查，不是工程師，給他們看花括號等於這一頁沒做。

15. `web/app.js` 的 `viewAccess`：權限自檢。整頁**沒有任何專用後端介面**，每個按鈕打的都是其他頁面在打的同一批介面，結果是伺服器當場回的。沒有可作弊的地方，所以沒法作弊——若為這頁單寫一個 `/api/demo/check`，它回什麼都是我說了算，證明力歸零。

    呈現分兩層。上層是業務語言：「查詢操作留痕 → ✕ 拒絕 · 此功能僅限組長、管理員」，管理層只看這一層。下層是折疊起來的等寬回執：`GET /api/audit 403 9ms` 加上後端原話，被問到「這是真的嗎」時當場展開。一個頁面服務兩種觀眾——純業務話會被懷疑是畫的，純 HTTP 又沒人看得懂。

    紅色照用，因為要的就是衝擊力；但每一條紅的旁邊跟一個綠色的「符合預期」，區塊頂上壓一句「8 項檢查 · 8 項符合預期 · 其中 3 項被正確攔截」。頁面的標題是好消息，紅色出現在裡面當證據。少了那句匯總，看到三行紅字的第一反應會是「你這系統有問題」，那就完全反了。

    三個「管理類」探針都打空目標，**任何角色執行都不會動到一行資料**：職員在 `Depends(require(...))` 就被擋下，根本進不到 handler；組長與管理員進得去，但刪除指向不存在的 id、匯入送的是無效檔案，所以 200 變成 404 與 400。這是這頁在演示現場不會翻車的保證。

16. `api/roadmap.py`：待辦與風險，十條。每條包含事項、狀態、為什麼它比寫程式慢、卡在誰那裡。

    這個介面沒有任何技術含量，但它是整個原型裡資訊量最大的一頁。原型能做的部分都做了，做不了的部分明確寫出缺什麼，而不是留空。

## L6 知識庫

獨立於業務資料的一條鏈路。這一層不讀業務表，業務層也不依賴它，兩邊只在 `api/knowledge.py` 處相接。

按序讀四個檔案加一個介面：

17. `knowledge/llm.py`：模型客戶端。走 OpenAI 相容端點，任何相容服務換個環境變數即可。沒有金鑰或 `DEMO_MODE` 打開時 `available()` 回傳 False，由呼叫端走降級路徑。

18. `knowledge/ingest.py`：切分入庫。按標題層級切段，不按固定字數硬切。規範類文件的一條條款就是一個語義單元，硬切會把條款劈成兩半，檢索出來的片段就沒法當作出處使用。每段保留檔名、標題路徑與原文起止行號。資料量小，索引放記憶體。

19. `knowledge/retrieve.py`：關鍵詞加權打分，標題命中權重高於正文，段落長度做歸一避免長段僅憑字數佔優。

    刻意不上向量檢索。規範問答的查詢詞與原文用詞高度重合，關鍵詞加權在這個場景效果穩定且完全可解釋，出錯能立刻看出是哪一步的問題。

    打分只算二元詞與英數詞，不算單個漢字。單字在中文裡太泛，「今天天氣如何」裡的單字會跟大量段落沾邊，實測會誤命中三段。只算二元詞才能把無關提問擋在門外，現在四個無關提問全部回傳空。

20. `knowledge/answer.py`：生成。把檢索回來的段落連同出處編號拼進提示詞，要求每句結論標註引自第幾段，並明確規定檢索結果裡沒有依據時必須回答不知道。

    無金鑰時走預置答案。預置答案不硬寫引用編號，而是記下它引自哪一節，渲染時按實際檢索結果解析出編號，對不上的條目直接丟掉。硬寫編號會在檢索結果變動時對不上，那種錯誤在演示現場最難解釋。

    這一條是整個模組的核心。受監管場景裡答錯比答不出來嚴重，所以設計目標不是什麼都能答，而是答的每一句都能追回原文，答不出來會明說。

21. `api/knowledge.py`：接收問題，轉調 `answer.py`，並寫一條留痕記錄誰問了什麼。

## L7 前端

單頁應用，無建置步驟，瀏覽器直接跑。三個 JS 檔按依賴順序載入，後面的用前面的。

按序讀五個檔案：

22. `web/tokens.css`：設計令牌。暖紙三階、森林綠、字級、圓角、陰影、三條緩動曲線，全部定義成 CSS 變數。後面所有樣式只引用變數，不寫死顏色。

    材質規則只有一條：毛玻璃是「外殼」的材質，不是「內容」的材質。側欄與右上角浮層用它，內容區一律實色。滿屏半透明會讓介面顯得廉價，高級感來自排版、留白與層級，不是來自材質特效。

    網頁字體由 `index.html` 以非阻塞方式載入，失敗時退到系統字體堆疊。現場沒有網絡時版面不會塌。

23. `web/style.css`：元件樣式。背景只有一層極淡垂直漸層加一層 2.2% 的顆粒。

    頁面的主結構是「區塊」，靠留白與一條髮絲線分隔，不套框；只有真正需要獨立成一張紙的東西才用卡片。表格去掉外框與底色，只留分隔線。主要動作是深苔綠實色配白字，檸檬綠全站只出現在狀態點、側欄選中點與引用編號上。

    字級跨度是這套設計的骨架：10.5px 的 mono 標籤、34px 的標題、13.5px 的說明。

24. `web/motion.js`：需要 JS 才做得到的三件事——列表錯峰入場、數字滾動、進度條生長。純 CSS 能做的都留在樣式表，不重複實作。

    全站只用三條曲線：`--spring` 交互反饋、`--glide` 位置移動、`--fade` 淡入淡出。`prefers-reduced-motion` 開啟時一律瞬時完成，不是放慢，是不做。

    側欄的選中態由一枚獨立的指示器負責，量測新舊位置後滑過去。整個導航共用一枚而不是每組一枚，因為每組一枚的話跨組切換時舊的消失、新的憑空出現，中間沒有位移可以動畫。外殼因此必須常駐，視圖切換只換 main 的內容。

    這一枚是液態玻璃。玻璃的三件事在 `style.css` 裡：身後折射（`backdrop-filter` 的模糊加提亮，提亮是關鍵，玻璃看得見是因為它比周圍亮一點）、自身厚度（上緣近白、下緣偏苔綠的斜向漸層）、邊緣掛光（頂緣一條高光、底緣一條較弱的回彈光、一圈髮絲邊，外加一層淺投影讓它浮起來）。

    「液態」來自位移時的擠壓回彈：走得越遠拉得越長，封頂 16%，形變原點放在行進方向的前緣，所以被拉長的是尾巴不是頭。位置走 `translate`、擠壓走 `scale`，這兩個是各自獨立的 CSS 屬性而不是同一條 `transform`，擠壓才能先回彈、位移還在走；合成一條的話中途改擠壓會把位移的過渡一併重啟。`prefers-reduced-motion` 開啟時整段瞬時完成。

25. `web/api.js`：前端唯一的請求出口。統一附加 token、統一解析、統一處理 401 跳登入與錯誤提示。所有視圖都不直接調 fetch。

    多一個 `probe()` 給權限自檢用。它和 `request()` 的差別只有一個但很關鍵：`request()` 遇到非 2xx 會拋錯，而且把狀態碼揉進了字串（「請求失敗（403）」），拿不到結構化的 status。`probe()` 把 `{ok, status, detail, count, ms}` 當**資料**回傳——那正是自檢頁要展示的東西。它也刻意不觸發全域的 401 跳轉：自檢頁本來就在打會被拒的介面，順手把人踢回登入頁的話整頁就白跑了。

    token 只存在記憶體，不落 localStorage。重整頁面即失效，每次開啟都必須重新登入。這既是鑑權演示的重點，也避免 token 留在瀏覽器裡。登出與切換帳號的入口在右上角常駐，演示時要頻繁切換三個角色，那個入口必須顯眼。

26. `web/ui.js`：渲染原件。表格、徽章、統計塊、進度條、空態、載入態、吐司，都是接收資料回傳 DOM 節點的純函數。視圖層只負責取數與組裝。`withCitations` 把答案裡的 `[1] [2]` 標成高亮，讓引用一眼可見。

    `mount(main, nodes, token)` 的 token 必須由呼叫端傳入，不能在 `mount` 裡讀 `main.dataset.token`：讀的時候拿到的永遠是「當前最新」那個號，跟自己比一定相等，於是過期的視圖會若無其事地把新視圖蓋掉。症狀是登入後立刻點側欄，落在新頁上的卻是今日工作台。非同步的續行必須自己記得屬於哪一輪，這件事只能靠傳參——這個 bug 真的發生過。

27. `web/orb.js` 與 `web/orb.wgsl`：液態玻璃球。著色器是 `orb.wgsl`，原文一行未改；`orb.js` 只負責跑它，uniform 種子照搬，只換掉十二個顏色槽位讓球落進本專案的色系，其餘每一個參數都保持原值。

    它只出現在一個地方：等模型回應時的思考膠囊。不當 logo，不當裝飾。WebGPU 不可用時靜默退到 CSS 畫的靜態球，裝飾件絕不拖垮頁面。

28. `web/app.js`：hash 路由，九個視圖。側欄沒權限的項目**顯示但掛鎖**，點下去跳到權限自檢並當場向後端驗證一次——真正的權限判斷在後端，前端顯示或隱藏入口都不構成安全邊界，但顯示至少讓邊界看得見。

    視野條（`paintScopeMeter`）常駐在內容區頂部，每一頁都在。放進 `main` 的話每次換視圖 `replaceChildren` 就把它沖掉了，所以 `main` 外面多包一層 `.content`。它把「看不到」量化成一句話：「另有 80 位住客、2 間院舍不在你的範圍內」。切換身分時這條會當場變長，觀眾不必記住上一個角色的數字。

    條上同時寫「負責 12」與「可查閱 30」。畫面上這兩個數字都看得到——住客主檔列的是可查閱的 30 位，合規看板算的是負責的 12 位——不把差別寫在條上，被問到時就變成解釋不清的破綻。

    權限不做成一個專門的展示頁。如果鑑權能力只活在某一頁裡，看的人會正確地判斷出那是做給他看的樣板。所以視野條常駐、每個禁用入口都掛鎖，自檢頁只是把這件事集中演一次。

## 這個原型刻意不做的事

排班引擎、交更流程、AI 月度報告、多租戶、離線暫存、資料遷移。

不是因為做不了，是因為它們需要的東西目前拿不到：業務規則要訪談、歷史資料要盤點、合規口徑要法務確認。全部列在系統內的「待辦與風險」頁，每條註明卡在哪裡。

原型用 SQLite，多人同時寫入會鎖表。正式環境必須改用 PostgreSQL，並以行級安全做院舍隔離，權限就不只靠應用層把關。

知識庫文件為示範文本，依公開資料改寫，非官方版本。所有住客與員工資料均為生成的示範資料，與任何真實個人無關。

本原型為自研。品牌、介面、資訊架構與資料模型均獨立設計，不沿用任何既有系統的名稱、版面或流程。
